# relation-graph · 人际关系图谱

把一个组织里的人际与利益关系沉淀成一张**可查询、可推理**的图。

它要回答的不是"画得好不好看",而是四个具体问题:

1. **谁和目标 X 有矛盾,并且我拉拢得动?**
2. **这里实际存在几个圈子,各自的核心是谁,谁在骑墙?**
3. **谁是绕不开的桥梁人物?我要接触某人,该托谁引荐?**
4. **哪些三角关系是不稳定的 —— 也就是局势最容易翻转的支点?**

跑在自己的电脑上,数据只存本地,手机通过浏览器访问,可"添加到主屏幕"当 App 用。

## 跑起来

**环境要求:** Python 3.9+,没有其他必需依赖。

```
git clone https://github.com/jaykuo6781-bit/relation-graph.git
cd relation-graph
python server.py
```

## 在手机上用

### 方式一:Tailscale(推荐)

只有你自己的设备能连,而且在外面用手机流量也能连。

1. 电脑装 [Tailscale](https://tailscale.com/download),登录
2. iPhone / Android 也装,**登录同一个账号**
3. 电脑上正常启动 `python server.py` —— 它会自动检测到 Tailscale 地址并打印出来
4. 手机浏览器打开那个地址

### 方式二:局域网(临时用)

手机和电脑连同一个 Wi-Fi 即可,但**同网络的其他人也能访问**。

```
python server.py --lan          # Windows 上是 run-lan.bat
```

启动时会打印手机该访问的地址。**在公司网络下不要用这个模式。**

### 添加到主屏幕

Safari 打开后 → 底部「分享」→「添加到主屏幕」。
之后从桌面图标进入是全屏无地址栏的,和原生 App 基本没有区别。

## 为什么手机不发热

这是这个项目在架构上唯一"讲究"的地方。

关系图最耗电的部分是**力导向布局的迭代计算**。常规做法是在浏览器里跑物理
模拟循环 —— 每秒几十帧、反复计算每个节点的受力,这正是手机发烫的原因。

这里把这一步整个搬到了电脑端:

```
电脑
 ├── 力导向布局迭代      → 算出每个节点最终的 (x, y)
 ├── Louvain 社区发现    → 派系归属
 ├── Brandes 中介中心性  → 桥梁人物
 ├── Dijkstra 最短路     → 引荐路径
 └── 结构平衡三角扫描    → 不稳定支点
        │
        │  HTTP 返回已经算好的坐标
        ▼
手机
 └── 只做一件事:把坐标画成静态 SVG
     · 没有物理循环,没有逐帧计算
     · 平移缩放只改一个 CSS transform,由 GPU 合成
     · → CPU 基本闲置
```

布局结果按数据版本号缓存,数据不变就不重算;重算时以上一次的坐标为起点,
所以图不会每次大变样,你对它的空间记忆能保留下来。

## 四个分析功能

| 功能 | 算法 | 说明 |
|---|---|---|
| **找敌人的敌人** | 自定义评分 | 对目标 X,找出所有与他有矛盾的人,按 `矛盾烈度 × 可拉拢度` 排序。可拉拢度含你与此人的直接交情,以及经由共同好友的二跳路径。如果某人跟你也不对付,分数会被压到接近零 —— 他不会帮你。 |
| **派系识别** | Louvain 社区发现 | 只用**正向关系**聚类(敌对关系不构成"一伙的")。圈内连接最强的是核心;对外连接占比超过四成的标记为骑墙。 |
| **关键人物 / 引荐路径** | Brandes / Dijkstra | 中介中心性衡量"绕不开"的程度。引荐路径沿正向关系走,边的代价取 `1/强度` —— 交情越铁这一跳越便宜,所以算法优先选强关系链而非单纯的短链。 |
| **不稳定三角** | 海德结构平衡理论 | 三条边的符号相乘为负即不稳定。`++-`(我的两个朋友互相敌视)和 `---`(三人互相敌对)都有内在张力,是局势最可能翻转的地方。按撬动价值排序,并指出撬哪条边最省力。 |

算法全部手写,没有引入图计算库 —— 百来号人的规模下任何算法都是毫秒级的,
手写的好处是"谁值得拉拢"这类评分逻辑完全可控,可以随时按实际情况调。

## 五种录入方式

| 方式 | 适用场景 |
|---|---|
| 网页表单 | 日常随手补一条 |
| 通讯录 / 表格导入 | 第一次铺底建人。粘 `姓名,部门,职位`,或从 Excel 直接复制 TSV |
| 批量文本导入 | 第一次铺底建关系。`张三-李四:敌对3`,分隔符很宽容 |
| 随手记事件 | 积累证据链。以后翻档案能看到当初为什么给这个分,而不只剩一个数字 |
| **故事解析(可选)** | 粘一段话,模型抽成候选清单,**每条附原文摘录**,人工逐条审核后入库 |

故事解析需要配置 `OPENAI_API_KEY` 环境变量(默认用 `gpt-4o-mini`)。
小模型会漏抽也会看错人,所以这个功能的设计前提就是**人工审核**:
每条候选都必须附上原文摘录,你扫一眼就知道它有没有编。
模型调用全部封装在 `llm.py` 一个文件里,换供应商只改这一处。

不配置也完全不影响其余所有功能。

## 数据模型

| 表 | 说明 |
|---|---|
| `person` | 姓名、别名、部门、职位、标签、备注,以及"我是谁"的标记 |
| `relation` | 关系:`(a, b, 类型, 强度)`,强度 −3..+3 |
| `event` | 随手记的事件,作为关系的证据 |
| `event_relation` | 事件与关系的关联 |
| `layout_cache` | 布局与分析结果的缓存,按图版本号失效 |

**关系类型**
正向:盟友、朋友、师徒、提携、同乡同学、利益共同体
负向:竞争、敌对、宿怨、利益冲突
中性:上下级、同事、认识

强度与类型是**互相独立**的两个维度 —— "竞争关系但私交不错"这种情况真实存在,
所以 `竞争 +1` 是合法的。同一对人也可以同时存在多种关系(既是上下级又是竞争),
图上会把它们的强度加总后作为这条边的综合权重。

无向关系统一按 `a_id < b_id` 归一化存储,所以不会出现"张三→李四"和
"李四→张三"两条重复边。有向关系(师徒、提携、上下级)保持 a→b 的语义。

## 自检

```
python selftest.py
```

`demo_seed.json` 里的关系不是随手编的:它预埋了**已知的派系结构**、
**已知的引荐路径**和**三个已知的不稳定三角**(见该文件的 `_expected` 字段)。
自检脚本拿这些预设值当标准答案逐条核对,而不是"程序没报错就算过"。

测试跑在临时数据库上,不会碰你的真实数据。

## 技术选型

刻意做成**零构建**:后端只用 Python 标准库(`http.server` + `sqlite3`),
前端是原生 JS + SVG,不用 npm、不用打包工具、不用框架。

理由:这是要长期跑在个人电脑上的私人工具。依赖越少越不会因为环境变动而烂掉,
双击一个 `.bat` 就能起来,三年后再打开大概率还能直接跑。
唯一的可选依赖是 `openai`,只有故事解析功能才需要。

图上的配色经过 CVD(色觉障碍)校验:派系用分类色板的前三槽,
正负关系用**蓝↔红**发散色板而不是红↔绿(那是最典型的色觉障碍陷阱),
负向边额外加虚线作为第二重编码 —— 不依赖颜色也能区分。
